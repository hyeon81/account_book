# 릴리즈 절차

이 문서는 저장소의 버전을 확정하고 Git 태그와 GitHub 릴리즈로 기록하는 절차다. `v0.1.0`은 문서·개발 환경의 첫 저장소 릴리즈이며, `v0.2.0`은 브라우저 저장소를 사용하는 가계부 UI 릴리즈다. API 서버·에이전트·DB와 운영 서비스 배포는 아직 포함하지 않는다.

## 버전과 기록의 기준

- 릴리즈 태그는 `vMAJOR.MINOR.PATCH` 형식으로 만든다. 저장소 루트 `VERSION`에는 접두사 `v`를 뺀 `MAJOR.MINOR.PATCH`를 적는다.
- 루트 `CHANGELOG.md`의 각 버전 절에 사용자와 개발자가 확인할 수 있는 변경 내용을 적는다. 예정된 변경은 릴리즈된 기능처럼 쓰지 않는다.
- 이후 UI 또는 Python 서버가 구현되어 `package.json`, `pyproject.toml`, 이미지 태그 등 버전이 필요한 파일이 생기면, 릴리즈마다 해당 버전도 `VERSION` 및 태그와 맞춘다. 현재 없는 파일은 버전 수정을 위해 새로 만들지 않는다.
- 애플리케이션 배포가 생기면 배포 대상과 방법, 롤백 절차를 이 문서에 추가한다. Git 태그를 만든 것만으로 서비스가 배포된 것은 아니다.

## 릴리즈 전 점검

1. `develop` 작업 트리가 깨끗한지 확인하고 릴리즈에 포함할 커밋을 확정한다. 원격 저장소에 연결할 수 있다면 원격 상태도 확인한다.
2. `CHANGELOG.md`에 새 버전, 날짜, 추가·변경·수정 사항과 알려진 제약을 기록한다. 실제 커밋과 문서를 근거로 작성한다.
3. `VERSION`과 이미 존재하는 패키지·배포 설정의 버전을 새 버전으로 맞춘다. README 등 버전 표시가 있다면 함께 갱신한다.
4. `pytest`, `python scripts/validate_docs.py`, `docker compose --env-file NUL config --quiet`을 실행한다. Windows에서는 `--env-file NUL`, Linux/macOS에서는 `--env-file /dev/null`로 실제 `.env`를 읽지 않는다. UI는 `ui`에서 `npm test`, `npm run lint`, `npm run build`를 실행하고 Docker 빌드·기동도 확인한다. 실패한 검사나 실행하지 못한 검사는 릴리즈 기록에 남긴다.
5. 변경 사항을 `develop`에 커밋한다. 비밀값이나 실제 `.env`는 읽거나 포함하지 않는다.

## 릴리즈 확정

1. `main`에 `develop`을 병합한다. 병합 전에 대상 브랜치에 예상치 못한 커밋이 없는지 확인한다. 충돌이 나면 해결한 뒤 검증을 다시 실행한다.
2. 병합된 `main`에서 `VERSION`과 변경 이력을 재확인하고 `vMAJOR.MINOR.PATCH` 주석 태그를 만든다. 이미 같은 이름의 태그가 있으면 덮어쓰지 않는다.
3. 원격 저장소에 접근 가능하면 `main`, `develop`, 태그를 푸시하고 원격 태그가 같은 커밋을 가리키는지 확인한다. 원격 작업이 실패하면 로컬 릴리즈와 원격 공개 상태를 구분해 보고한다.
4. GitHub 릴리즈를 요청받았다면 같은 태그로 릴리즈 페이지를 만들고 변경 내용·검증 결과·알려진 제약을 기록한다. 운영 서비스 배포는 별도 배포 절차와 접근 권한을 확인한 뒤 실행한다.

릴리즈 뒤에는 현재 브랜치를 `develop`으로 돌리고 작업 트리와 태그를 확인한다. 문제가 발견되면 기존 태그를 조용히 바꾸지 말고 수정 커밋과 새 패치 버전을 준비한다.
